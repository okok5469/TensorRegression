## 二、今天完成的分析结论

### 1. 对“跑了五天还没结束”的代码级判断

今天对以下路径进行了只读排查与本地抽样验证：

- `numerical_simulation/main.py`
- `numerical_simulation/runner.py`
- `numerical_simulation/methods.py`
- `numerical_simulation/data_generation.py`
- `src/tensor_abess/tensor/abess.py`
- `src/tensor_abess/tensor/bcd.py`
- `src/tensor_abess/group/adaptive.py`
- `src/tensor_abess/group/bess_fix.py`
- `src/tensor_abess/group/splicing.py`
- `src/tensor_abess/utils/init.py`
- `src/tensor_abess/utils/glasso.py`

结论如下：

1. **没有发现明确的死循环证据**；
2. 当前 full 主程序更像是“任务量巨大 + 旧版本缺乏中间进度落盘”，而不是“程序卡在无穷循环里”；
3. 慢的主要来源不是 Tensor-ABESS 主方法本身，而是对比方法尤其：
   - `Tensor-GLasso`
   - `Vector Lasso`
4. 最重开销来自：
   - `lambda × CV × ISTA` 多层嵌套；
   - 多场景、重复次数、外层循环叠加；
   - full 配置下默认场景总数较多。

### 2. 对 full 任务规模的判断

原始 full 配置下，总体任务量非常大：

- baseline + 4 组单因子实验；
- 每组包含多个 scenario；
- 每个 scenario 需要重复多次；
- 每个 repetition 跑 4 个方法。

因此，即使程序没有错误，在集群 CPU 环境下跑到“数十小时甚至多天”也是可能的。

### 2. 为数值模拟运行层增加“可观测 + 可续跑”能力

修改：

- `numerical_simulation/main.py`
- `numerical_simulation/runner.py`

具体落地点如下。

#### （1）full 默认重复次数下调

将 full 默认：

- `n_reps: 50 -> 10`

目的：

- 先保证实验可观测、可重跑；
- 先拿到一版稳定输出，再决定是否扩大到更高重复次数。

#### （2）新增 `--resume` 参数

在主入口中增加：

- `--resume`

作用：

- 当任务中断后，可以在同一个输出目录上继续跑；
- 避免已完成 repetition 被重复计算。

#### （3）每个 repetition 完成后立刻写盘

当前实现已改为：

- 每完成一个 repetition，立即将结果刷入 `raw_results.csv`；
- 不再等整套 full 全部结束后才第一次看到主要结果文件。

作用：

- 集群运行时更容易判断任务是否在持续推进；
- 中途被杀后损失更小。

#### （4）增加进度日志

当前实现会在每个 repetition 完成后输出一行进度，例如：

- 当前完成了多少 repetition；
- 当前在哪个实验组；
- 当前在哪个 scenario；
- 当前是第几个 rep。

作用：

- 运行时可以直接从日志判断作业是否在前进；
- 避免再次出现“长时间无输出、无法判断是否卡死”的问题。

#### （5）增加 checkpoint manifest

新增 checkpoint 机制核心信息文件：

- `checkpoint_manifest.json`

作用：

- 记录本次 suite 的基准配置与 `n_reps`；
- 在 `--resume` 时检查配置是否兼容；
- 防止把不一致的老结果和新任务错误拼接在一起。

#### （6）支持同一输出目录按实验组分批续跑

本次补齐后的行为是：

- 可以先跑 `snr`；
- 再用同一 `output-dir` + `--resume` 跑 `sample_size`；
- 再继续 `dimension`、`correlation`；
- 已完成的批次不会因为新批次而被静默丢掉。

这点是今天专门补测并修正过的关键行为。

## 四、今天发现并处理的一个运行层问题

### 集群报错：`TypeError: __init__() got an unexpected keyword argument 'resume'`

今天已定位该问题的根因：

- 不是算法错误；
- 不是新加的 `resume` 逻辑本身有数学问题；
- 而是**集群上的 `main.py` 和 `runner.py` 版本不同步**。

具体表现为：

- `main.py` 已经传入 `resume=...`；
- 但集群上的 `ExperimentSuiteConfig` 仍然是旧版，没有 `resume` 字段；
- 所以构造 dataclass 时直接报参数不兼容。

处理结论：

- 集群上后续运行必须保证新的 `numerical_simulation/main.py` 与 `numerical_simulation/runner.py` 一起同步；
- 不能只更新其中一个文件。

## 七、当前结论

### 1. 关于程序本身

当前更稳妥的判断是：

- **没有发现明确死循环证据**；
- 程序长时间运行更像是**对比方法过慢 + 旧版不可观测**；
- 因此不能简单下结论说“程序完全没问题”，但也**没有发现足以支持“已经陷入循环”的证据**。

### 2. 关于旧集群任务

如果旧任务：

- 仍然持续占用 CPU / 内存；
- 日志仍在刷新；
- 结果目录仍在正常推进；

那么继续等待是可以的。

但由于旧版缺乏足够的中间可观测性，判断成本很高，因此更推荐使用今天改过的新版本重新提交。

### 3. 关于新版本运行方式

今天已经给出推荐的新运行方式：

```bash
python numerical_simulation/main.py --profile full --experiments snr --output-dir numerical_simulation/outputs_full_v2
python numerical_simulation/main.py --profile full --experiments sample_size --output-dir numerical_simulation/outputs_full_v2 --resume
python numerical_simulation/main.py --profile full --experiments dimension --output-dir numerical_simulation/outputs_full_v2 --resume
python numerical_simulation/main.py --profile full --experiments correlation --output-dir numerical_simulation/outputs_full_v2 --resume
```

说明：

- 不需要手动先创建 `outputs_full_v2`；
- 程序会自动创建输出目录；
- 但必须保证集群当前目录对该路径有写权限。
