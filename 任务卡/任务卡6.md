# 任务卡6：Tensor-ABESS 性能归因、LEMON 实证重跑与团队交付

## 一、任务背景及总体目标

本项目当前正式算法为：

**`v5.2-search-final`（D2，已批准发布）**

算法经历以下版本：

- `v5-original`：原始算法。
- `v5.1-bcd-fix`：修复 fixed BCD 搜索中的损失回升、循环和最优状态保存问题。
- `v5.2-search-final`：在 v5.1 基础上，将全局精修的候选规模网格改为旧 caps 内的完整合法整数枚举。

v5.2 保留原 Group-BESS、初始化、逐模 caps、MSIC 公式及默认参数。

目前 v5.2 的正式数值模拟已经完成：

- 14 个场景标签；
- 每场景 50 次重复；
- 700 个数据任务；
- 2800 条方法结果；
- 工程完整性验收通过。

但是，与 `v5-original` 严格匹配输入的比较发现：

| 指标 | v5-original | v5.2 |
|---|---:|---:|
| Exact | 138/700 | 182/700 |
| 平均 PMSE | 2.236761 | 2.381274 |
| 平均 Mode-F1 | 0.751917 | 0.753593 |
| 平均拟合时间 | 25.03 s | 31.38 s |

新版改善了部分场景的真实支撑恢复，但整体平均 PMSE 恶化约 6.46%。

其中：

- n=400：Exact 从 1/50 提升到 49/50，PMSE 改善。
- n=100：Exact 仍为 0/50，PMSE 恶化约 24%。
- 低 SNR：预测效果仍然不稳定。
- rho=0：PMSE 恶化明显。

需要解释这些现象，并检验新版算法在真实脑数据上的实际表现。

**本任务不修改正式算法、不调整 caps/MSIC、不覆盖旧结果。**

# P0：v5 → v5.1 → v5.2 性能归因

## P0.1 目标

目前正式完整模拟直接比较：

\[
v5\longrightarrow v5.2
\]

但这中间存在两项修改：

\[
\underbrace{v5\rightarrow v5.1}_{BCD正确性修复}
\]

\[
\underbrace{v5.1\rightarrow v5.2}_{A2规模网格补全}
\]

因此，需要拆分两次修改的影响。

**目标是回答：**

- BCD 修复对支撑恢复和预测性能分别造成什么影响？
- A2 网格补全究竟改善了哪些场景？
- n=100 的恶化是否主要由 BCD 修复引起？
- n=400 的巨大恢复收益是否主要由 A2 带来？
- 预测恶化是否由少数严重过拟合模型主导？

不能单凭 v5 与 v5.2 的性能差异，把变化归因于 A2。

## P0.2 三版本严格配对

使用已经冻结的三个算法源码版本，分别加载、调用。

必须使用完全相同的：

- 训练和测试数据；
- DGP 配置；
- 随机种子；
- 初始化参数；
- MSIC 设置；
- 容量限制；
- 评价方式。

先检查核心源码指纹和实际 import 来源。

建议在隔离的 Python 进程中加载各版本，不得通过临时覆盖正式 `src/` 来切换算法。

已有 v5、v5.2 的正式输出应优先读取，不重新运行这些版本。

**只需要补跑 v5.1 的 Tensor-ABESS。**

如果正式输出中没有保存完整训练数据，则按冻结生成器、配置和种子重新生成，并与历史指纹逐项核对。

不得直接假定相同种子必然生成完全相同的数据。

## P0.3 选择诊断场景

优先选择：

| 场景 | 为什么要看 |
|---|---|
| n=100 | 新版 PMSE 明显恶化 |
| n=400 | 新版 Exact 大幅改善 |
| SNR=0.5 | 弱信号下预测困难 |
| rho=0 | 相关性变化下恶化明显 |
| 基准 n=200、SNR=2 | 观察通常设置下的变化 |

建议对这五个场景各50次原始重复执行 v5.1 配对诊断。

先对每个场景进行少量任务的运行检查，确认版本与输入正确后，再运行完整配对。

注意跨场景可能共享同一完整输入，应识别并尽量复用等价计算，但仍保留各场景标签对应的统计结果。

如发现其他任务具有更大的性能异常，可额外纳入个案分析，但不能改变上述事先确定的主比较范围。

### 特别检查 n=100

历史 n=100 时：

\[
caps=(4,4,4).
\]

原启发式网格已包含 1～4 的全部整数。

因此，在这些任务中，v5.1 和 v5.2 的规模集合预期应一致。

必须检查实际候选枚举、顺序、并列选择及最终拟合是否一致。

若两版本出现差异，逐项解释原因；不能直接将差异归因于 A2 新增候选。

## P0.4 比较指标

输出三版本的：

- PMSE、signal MSE、REE；
- Exact、Mode-F1、Element-F1；
- 最终 \(q\)；
- 三模支撑规模和位置；
- 训练 RSS；
- 最终 MSIC；
- 训练与测试误差差距；
- 候选数量；
- 算法耗时。

对每个样本分别计算：

\[
\Delta_1=PMSE_{v5.1}-PMSE_{v5}
\]

\[
\Delta_2=PMSE_{v5.2}-PMSE_{v5.1}.
\]

并比较：

\[
\Delta_{\mathrm{total}}
=PMSE_{v5.2}-PMSE_{v5}
=\Delta_1+\Delta_2.
\]

使用配对统计比较，而不是分别比较两个不匹配实验的均值。

报告胜/平/负次数、均值、中位数、极端差值及描述性不确定性。

14个标签含重复数据，不能把700任务当作700个独立同分布样本来进行统计推断。

# P2：分析完整模拟中预测恶化的机制

完成 P0 和本地 LEMON 后，再开展这一阶段。

## P2.1 研究目标

重点解释：

**为什么更充分的支撑搜索有时提高 Exact，却导致更大的 PMSE？**

不要继续修改算法，先研究原因。

## P2.2 按配对数据进行误差诊断

从正式700任务中提取新旧同任务的：

\[
\Delta PMSE_i
=PMSE_{v5.2,i}-PMSE_{v5,i}.
\]

统计：

- 改善、持平、恶化的次数；
- 恶化幅度最大的任务；
- 对总体平均恶化贡献最大的任务；
- 大误差是否集中于 n=100、弱 SNR、rho=0 等场景；
- 不同支撑规模下的训练和测试误差。

注意已有结果为：

```text
新版改善：99
相同：507
新版恶化：94
```

即改善与恶化次数比较接近，但总体平均 PMSE 仍变差。

要检查是不是存在少量影响很大的失败模型。

区分平均数、中位数、分位数和尾部风险。

## P2.3 分析模型复杂度

重点研究：

\[
q=s_1s_2s_3
\]

及：

\[
\frac{q}{Q},
\qquad
Q=\lfloor0.7n\rfloor.
\]

检查恶化任务中：

- 是否选择了接近容量上限的模型；
- 训练 RSS 是否大幅下降；
- 测试 PMSE 是否明显上升；
- 支撑位置是否更加不稳定；
- 是否存在估计方差增大的证据。

区分：

1. 候选搜索增加带来的影响；
2. fixed BCD 修复带来的影响；
3. MSIC 在候选集合变化后的选择效应；
4. 原 caps 导致的模型不可达；
5. 数据本身的小样本或弱信号困难。

不能仅看到 q 较大就断言所有恶化都由过拟合引起。

如果正式记录没有保存完整候选路径或 OLS 数值诊断，则只对事先选定的代表案例重新计算，并独立保存，不更改700份正式结果。

## P2.4 研究恢复与预测的权衡

将700组结果按以下情况分开：

- 新版 Exact 改善且 PMSE 改善；
- 新版 Exact 改善但 PMSE 恶化；
- 新版 Exact 不变但 PMSE 改善；
- 新版 Exact 不变但 PMSE 恶化；
- 新版丢失原本的正确支撑。

记录各组数量及主要场景。

对包含噪声的预测误差、signal MSE 与系数 REE 分别分析，避免把一种指标的改善直接等同于其他指标的改善。

尤其讨论：

**真实支撑恢复成功并不必然意味着有限样本预测误差最低。**
